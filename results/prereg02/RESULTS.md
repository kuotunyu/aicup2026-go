### 對照組重讀和帳上的差異（和登記的偏離；已查清後才採用）

- **偏離**：PREREG_02 1.3、2.3 規定重讀的 prereg01 分數要和帳上完全相同，不同就停下來查、查清前不採用。這次在小數點後第 15–16 位不同：競賽二每題平均 0.4919948709488189 → 0.49199487094881483、分等級平均 0.4908937784188385 → 0.49089377841883897；競賽一 0.3668476608218301 → 0.36684766082183023。H2R 和 H2P 是在同一行指令裡接連打分的，發現差異時 H2P 已經打完，所以沒能在兩者之間停下；兩者互不影響。判定是在查清之後才做的。
- **原因：打分用的 Python 版本不同**。prereg01 用沒加路徑的 `python`（本機 anaconda 的 3.10.9）打分（本對話 2026-09-25T19:28Z 的打分指令），這次用 repo 的 `.venv`（3.12.13）。`tools/score.py` 用內建 `sum()` 算平均，從 `2e2ad8a` 起沒改過；3.12 把內建 `sum()` 對浮點數改成補償加總（`sum([0.1]*10)` 在 3.10 是 0.9999999999999999，3.12 是 1.0）。
- **證據（都沒有再讀答案）**：
  - 兩次的預測檔、答案檔 SHA-256 相同；帳上的完全猜中率、差一級率相同，反推題數 525、698。用這兩個題數精確算出、正確捨入的平均正好等於這次的值，3.10 的值差 4e-15（`checks/reference_reread_sumcheck.py`、`.txt`）。
  - 結果核對代理（workflow `wf_75ba0b3c-9f4`）另外做的檢查：把 525 個 1、698 個 e^-1、366 個 0 隨機排 20,000 次，照 3.10 的方式逐項相加，有 2.6% 正好得到舊值、從來沒得到新值；用 3.12 內建 `sum` 則每次都是新值；兩個版本的 `math.exp(-1..-4)` 完全相同；競賽一第 2–5 名的題數只有一種分法能正確捨入成新值。
- **結論**：差異只是浮點捨入，不影響判定。
- **之後的做法**：一律用 `.venv`（Python 3.12）打分（寫進本資料夾 `CLAUDE.md`）；事前登記 03 起，重讀相等的定義改成「題數相同，而且差距 ≤ 1e-12」，並記錄打分用的 Python 版本。

## 注意事項與揭露

- **競賽一的分數高度依賴切法**：本機驗證集是在同一位玩家的棋裡隨機切（`tools/make_val.py`）。fit 模擬池上只用開局時，隨機切 0.8953、照檔案順序切 0.7436、執色分開 0.2082（`explore/opening_player_sim.json`）。三層防護和 11/04 的 T4 檢查就是為這個登記的。
- **接著訓練不能逐位元重現**：webdataset 的 `shuffle(1000)` 用時間當種子（PREREG_02 rev 4 第 8 節第 7 條）。
- **開局特徵的設計是在訓練玩家上探索後決定的**（PREREG_02 第 3 節）：競賽二開局 n-gram 的 M＝12、α＝20 在 inner 上探索後定（所以 inner 交叉驗證略為樂觀；M＝12、α＝60 的格子是凍結後才補算的，見 PREREG_02 rev 2 ③）；競賽一的 token 設計（前 10 手、兩套 token、1＋ln 次數、候選池 IDF）在 fit 玩家的模擬池上探索後定。都在 `explore/`，本機驗證集沒有參與，驗證集的分數不受影響。
- **開發時的預覽**：開發競賽一工具時曾在候選檔上跑過一次「只用開局」清單的自我檢索（PREREG_02 rev 3 第 7 節第 12 條），當時看到 Q22 0.876；這次正式選法跑出的 Q22 同為 0.8760。
- **打分的 Python 版本**：見上面「對照組重讀」一節。
- 執行帳號是使用者的 Google AI Pro 帳號；結果、權重（`epoch_6..9.pth`、`state.pt`）在該帳號 Drive 的 `C10/results/prereg02/`。
